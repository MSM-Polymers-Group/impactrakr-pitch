POST /v1/massids exige um campo deduplicationId no corpo — uma string opaca de até 255 caracteres, escolhida pelo cliente (não precisa ser um UUID: uma chave natural do seu próprio sistema, como um número de documento, serve). Uma retentativa com a mesma chave e o mesmo corpo resolve para o mesmo MassID em vez de criar um duplicado:POST /v1/massids requires a deduplicationId field in the body — an opaque string up to 255 characters, chosen by the client (it does not need to be a UUID: a natural key from your own system, like a document number, works fine). A retry with the same key and the same body resolves to the same MassID instead of creating a duplicate:POST /v1/massids exige un campo deduplicationId en el cuerpo — una string opaca de hasta 255 caracteres, elegida por el cliente (no necesita ser un UUID: una clave natural de su propio sistema, como un número de documento, sirve). Un reintento con la misma clave y el mismo cuerpo resuelve al mismo MassID en lugar de crear un duplicado:

POST /v1/massids
{ "deduplicationId": "erp-doc-48213", "polymerType": "PET", "plasticContentFactor": 1.0 }
→ 201 { "id": "«massidId»", "reference": "MS-2026-..." }

POST /v1/massids  (mesma chamada, de novo)(same call, again)(misma llamada, de nuevo)

Reusar a mesma deduplicationId com um corpo diferente não é tratado como retentativa — é um erro 409 DEDUPLICATION_ID_MISMATCH, porque a chave já significa outra coisa. Isso é deliberado: uma API de registry externa que este produto integra hoje devolve nesse caso um 409 sem id nenhum, deixando quem chamou sem saber se aquela era a sua chamada original ou um erro — aqui a resposta de sucesso sempre inclui o id, seja numa criação nova ou numa repetição.Reusing the same deduplicationId with a different body is not treated as a retry — it is a 409 DEDUPLICATION_ID_MISMATCH error, because the key already means something else. This is deliberate: an external registry API this product integrates with today returns a bare 409 with no id in that situation, leaving the caller unable to tell whether that was its original call or a mistake — here the success response always carries the id, whether it's a fresh create or a replay.Reutilizar la misma deduplicationId con un cuerpo diferente no se trata como un reintento — es un error 409 DEDUPLICATION_ID_MISMATCH, porque la clave ya significa otra cosa. Esto es deliberado: una API de registry externo con la que este producto se integra hoy devuelve en ese caso un 409 sin ningún id, dejando a quien llama sin saber si esa era su llamada original o un error — aquí la respuesta de éxito siempre incluye el id, sea en una creación nueva o en una repetición.

Essa mesma proteção agora cobre a criação de participantes (POST /v1/participants), a criação de endereços (POST /v1/addresses) e o registro de eventos num MassID (POST /v1/massids/:id/events) — todos exigem deduplicationId no corpo e respondem 409 DEDUPLICATION_ID_MISMATCH pelo mesmo motivo: chave reusada com um corpo diferente.This same protection now covers creating participants (POST /v1/participants), creating addresses (POST /v1/addresses), and recording events on a MassID (POST /v1/massids/:id/events) — all of them require a deduplicationId in the body and respond with 409 DEDUPLICATION_ID_MISMATCH for the same reason: a reused key with a different body.Esa misma protección ahora cubre la creación de participantes (POST /v1/participants), la creación de direcciones (POST /v1/addresses) y el registro de eventos en un MassID (POST /v1/massids/:id/events) — todos exigen un deduplicationId en el cuerpo y responden 409 DEDUPLICATION_ID_MISMATCH por el mismo motivo: una clave reutilizada con un cuerpo diferente.

Rate limitingRate limitingRate limiting

Todo endpoint autenticado tem um teto de requisições por minuto — por usuário ou por chave de API, dependendo de como você se autentica — e cada endpoint tem seu próprio orçamento independente: usar bastante um endpoint não consome o orçamento de outro para o mesmo chamador. Passar do teto devolve o 429 padrão do Nest:Every authenticated endpoint has a request-per-minute ceiling — by user or by API key, depending on how you authenticate — and each endpoint has its own independent budget: heavy use of one endpoint doesn't eat into another endpoint's budget for the same caller. Going over the ceiling returns Nest's standard 429:Todo endpoint autenticado tiene un techo de solicitudes por minuto — por usuario o por clave de API, según cómo se autentique — y cada endpoint tiene su propio presupuesto independiente: un uso intenso de un endpoint no consume el presupuesto de otro para el mismo llamador. Pasar el techo devuelve el 429 estándar de Nest:

→ 429 Too Many Requests
Retry-After: 42
X-RateLimit-Limit: 120
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1730000000

Os limites padrão são 120 requisições/minuto por usuário e 600 requisições/minuto por chave de API (integrações costumam chamar com uma chave de API, daí o teto mais alto). Uma exceção: GET /v1/audit-engagements/resolve-org (proteção contra enumeração de organizações) mantém um teto mais rígido de 10/min por usuário, independente do padrão geral.The default limits are 120 requests/minute per user and 600 requests/minute per API key (integrations tend to call with an API key, hence the higher ceiling). One exception: GET /v1/audit-engagements/resolve-org (organization anti-enumeration protection) keeps a tighter 10/min per-user cap, independent of the general default.Los límites por defecto son 120 solicitudes/minuto por usuario y 600 solicitudes/minuto por clave de API (las integraciones suelen llamar con una clave de API, de ahí el techo más alto). Una excepción: GET /v1/audit-engagements/resolve-org (protección contra enumeración de organizaciones) mantiene un techo más estricto de 10/min por usuario, independiente del valor general.
