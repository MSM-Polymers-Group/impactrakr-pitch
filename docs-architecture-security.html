Modelo de segurançaSecurity modelModelo de seguridad

Para revisores de TI e segurança: como o isolamento de tenant, a autenticação e a trilha de auditoria são de fato aplicados — não só descritos.For IT and security reviewers: how tenant isolation, authentication, and the audit trail are actually enforced — not just described.Para revisores de TI y seguridad: cómo se aplican realmente el aislamiento de tenant, la autenticación y el rastro de auditoría — no solo cómo se describen.

Isolamento multi-tenantMulti-tenant isolationAislamiento multi-tenant

  • Toda tabela operacional carrega um identificador de organização e tem Row-Level Security do PostgreSQL ativada e forçada — uma política exige que o id da organização bata em toda query, inclusive em uma que um desenvolvedor tenha esquecido de filtrar manualmente.Every operational table carries an organization identifier and has PostgreSQL Row-Level Security enabled and forced — a policy requires the organization id to match on every query, including ones a developer forgot to filter manually.Cada tabla operativa lleva un identificador de organización y tiene Row-Level Security de PostgreSQL habilitado y forzado — una política exige que el id de la organización coincida en cada consulta, incluidas las que un desarrollador olvidó filtrar manualmente.
  • O escopo da organização é definido por request via uma variável de sessão do banco, dentro da mesma transação da query — não existe caminho de código onde "esquecer de filtrar" vaze linhas de outro tenant.The organization scope is set per request via a database session variable, inside the same transaction as the query — there's no code path where "forgetting to filter" leaks another tenant's rows.El alcance de la organización se define por request mediante una variable de sesión de la base de datos, dentro de la misma transacción de la consulta — no existe una ruta de código donde "olvidar filtrar" filtre filas de otro tenant.
  • Migrações de schema rodam sob um papel separado e estritamente delimitado, o único autorizado a contornar a row-level security, e só para operações de schema, nunca para tráfego de aplicação.Schema migrations run under a separate, narrowly-scoped role that is the only one allowed to bypass row-level security, and only for schema operations, never application traffic.Las migraciones de esquema se ejecutan bajo un rol separado y estrictamente delimitado, el único autorizado a saltarse la row-level security, y solo para operaciones de esquema, nunca para tráfico de aplicación.

AutenticaçãoAuthenticationAutenticación

Usuários humanos se autenticam via AWS Cognito — armazenamento de senha, sessões e MFA (quando ativado) ficam delegados à infraestrutura gerenciada da AWS. Autorização (o que um usuário autenticado pode fazer) é auto-hospedada e baseada em papéis. Clientes máquina se autenticam com chaves de API por organização.Human users authenticate via AWS Cognito — password storage, sessions, and MFA (where enabled) are offloaded to AWS-managed infrastructure. Authorization (what an authenticated user can do) is self-hosted and role-based. Machine clients authenticate with organization-scoped API keys.Los usuarios humanos se autentican vía AWS Cognito — el almacenamiento de contraseñas, las sesiones y el MFA (cuando está activado) se delegan a infraestructura administrada por AWS. La autorización (lo que un usuario autenticado puede hacer) es autoalojada y basada en roles. Los clientes máquina se autentican con claves de API por organización.

Um modelo de ameaças por escritoA written threat modelUn modelo de amenazas por escrito

Existe um modelo de ameaças explícito e documentado catalogando quem poderia tentar acesso entre tenants (um atacante não autenticado, um usuário autenticado sondando IDs de recurso de outro tenant, um token adulterado ou expirado, um operador interno com acesso direto ao banco) e qual teste automatizado precisa existir e continuar passando para cada caso. Exemplo: um usuário da Organização B pedindo o recurso da Organização A por ID precisa receber um "não encontrado", nunca um "proibido" — uma resposta "proibido" já vazaria que o recurso existe.There's an explicit, documented threat model cataloguing who might attempt cross-tenant access (an unauthenticated attacker, an authenticated user probing another tenant's resource IDs, a tampered or stale token, an internal operator with direct database access) and which automated test must exist and stay green for each one. Example: a user from Organization B requesting Organization A's resource by ID must get a "not found," never a "forbidden" — a "forbidden" response would itself leak that the resource exists.Existe un modelo de amenazas explícito y documentado que cataloga quién podría intentar acceso entre tenants (un atacante no autenticado, un usuario autenticado sondeando los IDs de recurso de otro tenant, un token manipulado o vencido, un operador interno con acceso directo a la base de datos) y qué prueba automatizada debe existir y seguir en verde para cada caso. Ejemplo: un usuario de la Organización B que solicita el recurso de la Organización A por ID debe recibir un "no encontrado", nunca un "prohibido" — una respuesta "prohibido" ya filtraría que el recurso existe.

Integridade dos dadosData integrityIntegridad de los datos

Dois mecanismos independentes protegem a trilha de auditoria:Two independent mechanisms protect the audit trail:Dos mecanismos independientes protegen el rastro de auditoría:

  • Log de eventos em hash chain — toda mudança de estado é um evento cujo hash é calculado a partir do seu próprio conteúdo mais o hash do evento anterior. Editar ou apagar um evento passado quebra todo hash depois dele, então adulteração retroativa é detectável matematicamente.Hash-chained event log — every state change is an event whose hash is computed from its own content plus the previous event's hash. Editing or deleting a past event breaks every hash after it, so retroactive tampering is mathematically detectable.Log de eventos en hash chain — cada cambio de estado es un evento cuyo hash se calcula a partir de su propio contenido más el hash del evento anterior. Editar o eliminar un evento pasado rompe todos los hashes posteriores, así que la manipulación retroactiva es matemáticamente detectable.
  • Log de auditoria estruturado — de forma independente, toda mutação é registrada com um diff antes/depois, o usuário ou chave de API que agiu, o endereço IP, e um request ID.Structured audit log — independently, every mutation is logged with a before/after diff, the acting user or API key, IP address, and a request ID.Log de auditoría estructurado — de forma independiente, cada mutación se registra con un diff antes/después, el usuario o clave de API que actuó, la dirección IP, y un request ID.

Armazenamento & acesso ao bancoStorage & database accessAlmacenamiento y acceso a la base de datos

Documentos de compliance ficam em um bucket S3 com nenhum acesso público e nenhuma URL pré-assinada — todo download é transmitido através de uma chamada de API autenticada, então nada sobrevive a um logout como um link avulso. O banco de produção não tem endpoint público algum; acesso externo passa exclusivamente por um túnel de port-forwarding do AWS Systems Manager.Compliance documents live in an S3 bucket with no public access and no presigned URLs — every download is streamed through an authenticated API call, so nothing survives a logout as a standalone link. The production database has no public endpoint at all; external access goes exclusively through an AWS Systems Manager port-forwarding tunnel.Los documentos de compliance viven en un bucket S3 sin acceso público y sin URLs prefirmadas — cada descarga se transmite mediante una llamada de API autenticada, así que nada sobrevive a un cierre de sesión como un enlace independiente. La base de datos de producción no tiene ningún endpoint público; el acceso externo pasa exclusivamente por un túnel de port-forwarding de AWS Systems Manager.
