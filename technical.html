01 Overview

This page is written for the people who have to say yes or no before an integration happens: IT, security, and compliance reviewers. It is not a full API reference — it is the architecture, security, and data-handling picture you need to decide whether a pilot is safe to run.

02 Architecture & stack

The backend is organized as a set of bounded contexts (independent business modules — participants, mass-tracking records, homologation/permits, audit) rather than one shared codebase with shared tables. Each module owns its own PostgreSQL database on a shared RDS instance, so a bug in one module's queries cannot accidentally read or write another module's data at the database level, on top of the tenant isolation described in section 04.

The API layer runs on AWS ECS inside private subnets, reachable only through API Gateway with a VPC Link — the application servers themselves have no public IP and are not directly reachable from the internet. The dashboard is a separate Next.js application that talks to the API as a client, not as a trusted backend peer.

03 Data flow

Data does not go anywhere external until it has passed internal validation. The flow, end to end:

1. Ingestion

Today, the fastest and most common path for a new client is a structured Excel/CSV import — no engineering integration required to start a pilot. Direct API/ERP integration is available for machine clients today via API keys, and is the roadmapped default for scaled clients (see section 10).

2. Validation engine

Every record runs against the rule set(s) pinned to its project (regulatory + program-specific rules, versioned so a rule change never silently reclassifies historical data). Each rule fails as either a hard BLOCK (stops progression) or a FLAG (routes to human review).

3. Persistence + audit trail

Once validated, the record and every state change on it are written to PostgreSQL as an append-only, hash-chained event log (section 05), inside your organization's isolated tenant (section 04).

4. Dashboards

Role-based dashboards read from the validated data — nothing on a dashboard bypasses the validation step.

5. Optional registry submission

Only pre-validated, approved records are ever submitted to an external credit registry, and only for organizations that have opted into that specific integration. Nothing is pushed externally by default.

04 Multi-tenant security model

The platform is multi-tenant by design, and tenant isolation is enforced at the database layer, not only in application code:

  • Every operational table carries an organization identifier and has Postgres Row-Level Security enabled and forced — a policy requires organization_id to match the requesting organization on every single query, including ones a developer might forget to filter manually.
  • The organization scope is set per request via a database-level session variable (SET LOCAL), inside the same transaction as the query — there is no code path where "just don't filter" leaks another tenant's rows.
  • Schema migrations run under a separate, narrowly-scoped database role that is the only one allowed to bypass row-level security, and only for schema operations — never for serving application traffic.

Authentication

Human users authenticate via AWS Cognito — password storage, session handling, and (where enabled) multi-factor authentication are offloaded to AWS-managed infrastructure rather than custom-built. Authorization (what an authenticated user can actually do) is self-hosted and role-based. Machine clients (ERP integrations and similar) authenticate with organization-scoped API keys rather than user credentials.

A written threat model, not just a claim

There is an explicit, documented threat model that catalogues who might attempt cross-tenant access and how (an unauthenticated external attacker, an authenticated user probing another tenant's resource IDs, a tampered or stale token, an internal operator with direct database access), and for each one, which specific automated test must exist and stay green before code merges. For example: a user from Organization B requesting Organization A's resource by ID must get a "not found," never a "forbidden" — a "forbidden" response would itself leak that the resource exists.

Confirm before publishing: whether to state that this threat-model test suite runs in CI on every PR (recommended framing) versus a periodic/manual check — whichever is actually true today.

05 Data integrity & audit trail

Two independent mechanisms protect the audit trail from silent tampering:

Hash-chained event log

Every state change on a tracked record is stored as an event in an append-only log. Each event's hash is computed from its own content plus the previous event's hash, forming a chain — the same principle used in tamper-evident ledgers generally. Editing or deleting a past event breaks every hash after it, so retroactive tampering is mathematically detectable, not just against policy.

Structured audit log

Independently of the hash chain, every mutation across every module is logged with a structured before/after diff, the actor who made the change (a specific user or a specific API key — never an anonymous system write), the originating IP address, and a request ID that ties it back to a single API call. This is what a compliance or forensic review reads from, and it's queryable per record, per organization, or across an audit engagement.

06 Document & storage security

Compliance documents (permits, certificates, KYC records) are stored in AWS S3 with a deliberately unusual posture: the bucket has no public access and no presigned URLs. It is reachable only from inside the platform's own private network, and every download is streamed to the browser through an authenticated API call — there is never a standalone file URL that could end up in a browser's address-bar history, a clipboard, a screen-share, or a forwarded link and remain valid after the session ends. Revoking a user's session immediately revokes their ability to fetch any file, with nothing left over that a TTL has to expire on its own.

07 Database access

The production database has no public endpoint at all — it cannot be reached directly from the internet under any credential. External or manual access (for operations or debugging) goes exclusively through an AWS Systems Manager port-forwarding tunnel into the private network, which means there is no bastion host to keep patched and no database credential that is, by itself, exploitable from outside the network perimeter.

08 External auditor access

When an independent auditor needs to review a specific client's data, access is granted through an explicit, time-bounded engagement grant — not a standing account inside your organization:

  • The auditor requests access to a specific organization; that organization's own administrator must confirm it before anything is granted.
  • Access expires automatically (annual re-authorization by default) and can be revoked at any time by the organization being audited.
  • Both sides can see the current state: the organization sees which auditors currently have access to it, and the auditor sees which organizations they're currently engaged with.
  • An auditor never becomes a member of your organization's user roster — every read they make is checked against the current, active grant, request by request.

This is built, not just designed: request, confirm, revoke, and a scheduled job that auto-expires grants at the end of their validity window all exist in the codebase today.

Confirm before publishing: the mechanism above is implemented and covered by tests. Whether it has been switched on for real, paying customers yet is a rollout decision, not an engineering one — say "available" only once that's actually true.

09 Compliance posture

Being direct about where things stand, rather than rounding up:

What's real today: the tenant-isolation, audit-trail, and access-control mechanisms described above; production and development environments run in fully separate AWS accounts; the EU Waste Shipment Regulation (EU) 2024/1157 and the DIWASS digital exchange system it establishes are encoded directly into the validation engine's rule sets, versioned per project so a rule update never silently reclassifies past records.

What's on the roadmap, not done: a completed, certified GDPR/LGPD compliance program is not something to claim as finished today. A legal terms framework exists internally but is an explicit draft awaiting legal review before any external use — treat the technical mechanisms above as the foundation that program is built on, not the program itself.

Confirm before publishing: is there a target date for the GDPR/LGPD program and the legal-terms review worth stating here, or should this stay open-ended.

10 Integration paths

Today — fastest path to a pilot: structured Excel/CSV import. This is deliberate: it lets a client validate the platform against their real historical data before either side invests in an engineering integration.

Available today for machine clients: organization-scoped API keys for programmatic access, independent of the human-user authentication path.

Roadmapped: direct ERP/API integrations as the default onboarding path for larger clients, building on the same API-key authentication already in place.

Confirm before publishing: any timeline for the ERP/API integration roadmap, or keep it open-ended as above.

11 Engineering process

Every architectural choice that would be expensive to reverse, or that a future engineer would reasonably wonder about, is written down as an Architecture Decision Record (ADR): the context that forced the decision, the decision itself, alternatives considered and why they were rejected, and the consequences accepted. This is an internal engineering log, not marketing copy — it exists so decisions survive team changes and so "why does it work this way" always has a written answer.

12 Security FAQ

Where is our data hosted?

AWS, region eu-central-1 (Frankfurt, Germany) — both the development and production environments.

Who can see our data?

Only your organization's own authorized users by default, plus platform operators through a logged access path, and independent auditors only for the duration of an active, consented engagement grant (section 08). Row-Level Security enforces this at the database layer, not just in application logic.

Is our data automatically sent to any external registry or blockchain?

No. Nothing leaves the platform to an external registry unless your organization has explicitly opted into that specific integration, and even then only records that have already passed internal validation are ever submitted.

Can we get a security questionnaire response, SOC 2 report, or penetration test report?

Confirm before publishing: whether any of these exist today, and who owns fulfilling ad-hoc security-questionnaire requests from prospective clients.

What's the incident response process if something goes wrong?

Confirm before publishing: there's no publicly documented incident-response process yet — decide whether to state one here or point to a contact instead.

Do you support single sign-on (SSO)?

Not yet wired up. The identity provider (AWS Cognito) supports SAML/OIDC federation in principle, but no SSO integration exists in the codebase today — this is roadmap, not available.
